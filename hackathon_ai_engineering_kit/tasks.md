# Задания участникам

## Базовый уровень (новички, 20–30 минут)
Цель: сделать помощника полезнее, не переписывая приложение целиком.

1. Запустить API и открыть `/docs`.
2. Проверить три вопроса из `evals.json`.
3. Исправить поиск так, чтобы учитывался весь текст документа, а не только первые 260 символов.
4. Сделать ответ на вопрос без подтверждения безопасным: не выдавать найденный документ за достоверный ответ.
5. Добавить минимум два теста: на вопрос с ответом и на вопрос, ответа на который нет.
6. Подготовить 30-секундную демонстрацию.

Критерий готовности: ответы на известные вопросы ссылаются на правильные файлы, а при отсутствии информации сервис честно сообщает об этом.

## Продвинутый уровень (опытные разработчики, 20–30 минут)
Выберите два или более улучшения:

- Вернуть top-3 релевантных фрагмента и убрать дубликаты источников.
- Улучшить ранжирование: BM25, нормализация токенов или взвешивание совпадений в заголовке.
- Добавить порог релевантности и корректный отказ при слабом совпадении.
- Реализовать оценку по `evals.json`: accuracy по ожидаемому источнику, доля корректных отказов, время ответа.
  Заготовка — `evaluation.check_all_questions()`. Негативные вопросы (`expect_abstain`) и поле `must_contain` уже есть в `evals.json` — расширьте набор своими.
- Добавить structured output: `answer`, `sources`, `confidence` или `abstained`.
- Добавить таймауты, обработку ошибки провайдера и понятный fallback.
- Добавить проверку prompt injection: текст документа — данные, а не инструкции для модели.
- Сравнить результаты baseline и улучшенной версии на одном и том же наборе вопросов.
- Сравнить `retrieval=lexical|semantic|hybrid` через `python compare_backends.py` и объяснить, где каждая половина проигрывает.

## Общие правила
- Не меняйте набор тестов так, чтобы искусственно улучшить результат.
- Не записывайте API-ключ в код или git.
- Не утверждайте, что система «точная на 100%» по маленькому тестовому набору.
- Защита должна включать один успешный и один неуспешный сценарий.
