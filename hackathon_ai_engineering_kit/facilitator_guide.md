# Памятка ведущему

## Цели
Показать инженерный цикл: собрать MVP → измерить качество → найти дефект → исправить → повторно измерить.

## Расписание на 90 минут
- 0–10: показать сбойный ответ и сформулировать критерий успеха.
- 10–20: схема RAG и минимальная архитектура.
- 20–50: участники запускают проект и улучшают поиск/отказ.
- 50–70: челлендж на контрольных вопросах; блок «семантика против лексики» (см. ниже).
- 70–85: демонстрации и сравнение результатов.
- 85–90: выводы о минимальном стеке, распределении задач и доказательстве качества.

## Намеренно оставленные ошибки в стартовом коде
1. `retrieval.py`: анализируется только первые 260 символов каждого документа. Факты ближе к концу файла могут не находиться.
2. `retrieval.py`: `top_k=1`; система использует только один фрагмент, даже когда вопрос требует нескольких источников.
3. `app.py`: отсутствует порог релевантности. Любое слабое совпадение может попасть в контекст LLM.
4. `app.py`: источник возвращается даже при слабом совпадении, что создаёт ложное впечатление обоснованности.
5. В demo-режиме возвращается первая строка документа, а не ответ по смыслу. Это намеренная заглушка, а не ошибка LLM.

Не раскрывайте этот список участникам до челленджа.

В `semantic.py` намеренных ошибок нет: это эталонное решение для блока про семантику.
Не показывайте его до 50-й минуты.

## Подсказки для разбора
- Сначала исправить индексирование полного документа и посмотреть на вопросы, которые ранее не находились.
- Затем добавить порог релевантности и тест на неизвестный вопрос.
- Только после этого улучшать top-k и ранжирование.
- Источники должны отражать реальные фрагменты, использованные для ответа.
- Разделять качество retrieval и качество генерации: неверный контекст нельзя надёжно исправить одним промптом.
- «Было/стало» фиксировать одной командой: `python evaluation.py --verbose` до и после правок
  (baseline — `hit@1 10/25`, отказы `2/4`); для сохранения результата добавьте `--json before.json`.

## Семантический поиск: блок на 10 минут (после челленджа)

Цель: показать, что «векторный поиск» не отменяет лексику, а дополняет её.

Цифры для слайда — из `python compare_backends.py` (25 вопросов с ответом и 4 без ответа, только retrieval, LLM не вызывается):

| режим | hit@1 | hit@3 | отказы | что это |
|---|---|---|---|---|
| `lexical` | 10/25 | 10/25 | 2/4 | стартовый `retrieval.py` с недочётами, режим по умолчанию |
| `semantic` | 20/25 | 24/25 | 0/4 | абзацные чанки + статические эмбеддинги + косинус |
| `hybrid` | 21/25 | 24/25 | 0/4 | RRF: лексика + эмбеддинги |

Обратите внимание на последний столбец: оба «умных» режима выдумывают источник там, где ответа в документах нет вовсе.
Это готовый аргумент, почему порог и негативные вопросы нужны раньше, чем эмбеддинги.

Все три вызываются в `/docs` одним полем: `{"question": "...", "retrieval": "lexical|semantic|hybrid"}`.

Порядок показа:

1. **Семантика выигрывает.** «Нужна ли страховка для участия?»: `lexical` → пусто, `semantic` и `hybrid` → `08_support_and_safety.md`.
   Спросите: «Почему лексика не нашла?» — в документе «полис страхования», а слова «страховка» нет.
   Второй пример: «Можно ли участвовать вдвоём?» — лексика отдаёт `07_presentation.md`, семантика — `04_eligibility.md`.
2. **Семантика проигрывает.** «Сколько времени дают на ответ жюри?»: лексика точно попадает в `07_presentation.md`,
   семантика уходит в `06_judging.md`, а гибрид — в `08_support_and_safety.md`. Вывод, который должны сформулировать
   участники: эмбеддинги не различают похожие по смыслу регламентные документы.
   (В demo-режиме текст ответа строится по первому фрагменту — это недочёт №5, его не надо путать с качеством поиска.)
3. **Гибрид спасает там, где обе половины ошиблись.** «Что нужно разработать по кейсу?»: `lexical` → пусто,
   `semantic` → `05_requirements.md`, `hybrid` → `09_case.md`. Это и есть аргумент за RRF.
4. **Честная граница.** «Сколько раз будут проверять прогресс?» не находит ни один режим: в программе три чек-поинта,
   но слова «прогресс» нет ни в одном документе. Хороший момент сказать, что никакой «просто семантический поиск» не гарантирует ответа.

Что проговорить про ограничения:

- Порог по косинусу нельзя ставить «на глаз»: вопрос без ответа «Будет ли онлайн-трансляция хакатона?» даёт 0.478,
  а самый слабый корректный вопрос — 0.304. Любой порог между ними режет правильные ответы или пропускает выдуманные.
  Поэтому негативные кейсы в `evals.json` нужны до калибровки порога.
- `score` в ответе не сравним между режимами: у `semantic` это косинус, у `hybrid` — сумма 1/(60+rank).
  Для гибрида сравнивать абсолютные числа бессмысленно, важна позиция.
- Модель (`minishlab/potion-multilingual-128M`) весит ~530 МБ и ставится отдельно:
  `pip install -r requirements-semantic.txt`. Без неё `semantic`/`hybrid` отвечают 503 с подсказкой, а `lexical` работает как обычно.
- Для офлайн-площадки скачайте модель заранее (см. README, раздел про `EMBED_MODEL`): интернета на мероприятии может не быть.
- Не тащите на МК векторную БД: 162 чанка и `numpy`-умножение дают меньше 2 мс на запрос.

## Как распределить работу в команде
- Retrieval: поиск, ранжирование, источники.
- API/LLM: контракт, промпт, вызов провайдера.
- Evaluation: тестовый набор, метрики, регрессии.
- Интеграция/демо: запуск, smoke test, демонстрационный сценарий.

Для команд из 2 человек объедините роли: retrieval + evaluation и API/LLM + интеграция.

- [ ] `pytest -q` проходит.

- [ ] Если показываете семантику: `pip install -r requirements-semantic.txt` и `python compare_backends.py` отрабатывают; модель эмбеддингов скачана заранее.
- [ ] `uvicorn app:app --reload` запускается.
- [ ] `/docs` открывается.
- [ ] Если используется LLM: `python check_llm.py` успешно отвечает на каждом нужном окружении.
- [ ] Проверены лимиты, биллинг, доступность сети и политика использования провайдера.
- [ ] Есть план B: demo-режим без внешнего API.
